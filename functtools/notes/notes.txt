The Reality: Inheriting directly from built-in types like dict or list is a notorious trap in Python. Because built-in types are written in C for performance, their internal C-methods often bypass overridden Python methods. For example, if you override __setitem__ to add validation, but someone calls .update() on your custom dict, CPython's internal implementation might modify the dictionary directly without triggering your Python __setitem__ validation!

The Solution: Inheriting from collections.abc.MutableMapping forces you to implement a few core hooks (__getitem__, __setitem__, __delitem__, __iter__, __len__), and Python automatically gives you a fully functional, safe dictionary wrapper that plays nicely with all methods.

To truly protect a mutable collection via a property, you must return a shallow copy or a tuple so external code can read it, but never mutate it directly

collections.abc (Abstract Base Classes for Collections):

Instead of inheriting from list or dict (which can lead to weird bugs because of built-in implementation details), you inherit from or implement protocols like collections.abc.Mapping, collections.abc.Sequence, or collections.abc.Container. This is how you build professional custom collections.

1. What is the Exact Minimum? (The 5 Abstract Methods)
MutableMapping actually requires 5 abstract methods, not just two. If you fail to implement even one of these five, Python will raise a TypeError the moment you try to instantiate your class:

__getitem__(self, key) — How items are fetched.

__setitem__(self, key, value) — How items are assigned.

__delitem__(self, key) — How items are deleted.

__iter__(self) — How you loop through keys.

__len__(self) — How you count the items.


2. Container (collections.abc.Container):

The Contract: Requires only __contains__(self, item).

What it gives you: It enables the in operator (e.g., "apple" in my_basket). Any class implementing __contains__ is a Container.


3. Sequence (collections.abc.Sequence):

The Contract: Requires __getitem__ and __len__.

What it gives you: It models ordered, indexable collections like lists or tuples. Inheriting from Sequence automatically gives you free mix-in methods like .index(), .count(), and full integer indexing/slicing support (my_list[1:3]).

typing.Protocol (Structural Subtyping / Interfaces):

Traditional OOP uses nominal subtyping (class Dog(Animal)). Protocol lets you use structural subtyping (duck typing with type safety): "If it has a quack() method, it's a Quacker, regardless of what class it inherits from." This is the exact philosophy behind FastAPI's dependency injection.



typing.Generic & TypeVar:

Crucial for writing reusable classes (like your Inventory or a custom data pipeline) that can enforce types dynamically (e.g., an Inventory[Item] that strictly accepts only Item instances).


typing.ClassVar vs Instance Variables:
# @dataclasses
Understanding the exact boundary between class-level data (shared across all instances) and instance-level data under type checkers.


typing.NamedTuple:

A lightweight, memory-optimized, type-hinted alternative to full classes for immutable data objects.
